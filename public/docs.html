2. المتطلبات الوظيفية وغير الوظيفية

2.1 المتطلبات الوظيفية (Functional Requirements) - ملخص

هذه الوظائف مبنية فعلياً في الكود (وليست افتراضات) - كل سطر هنا له Controller وForm Request وRoute مقابل:

  • FR-1..2: تسجيل/دخول العميل عبر OTP (3 خطوات) - CustomerAuthController
  • FR-3..9: تقديم طلب صيانة، عرض القائمة والتفاصيل، الإلغاء، الموافقة/الرفض على التشخيص - MaintenanceRequestController
  • FR-10..11: تشخيص الفني (تحديد القطع والوقت) وموافقة العميل مع خصم المخزون - Technician\MaintenanceRequestController + MaintenanceRequestController::approve
  • FR-16..20: تصفح الملحقات، السلة، الدفع (checkout) مجزأ حسب الصالة - AccessoryController / CartController / OrderController
  • FR-21: سجل الطلبيات للعميل - OrderController::index
  • FR-22..23: استشارات AI (Gemini) واستشارات فنية بشرية - Customer\ConsultationController
  • FR-25: إيجاد أقرب صالة بالإحداثيات (Haversine) - ShopService
  • FR-28: إدارة الصالات من الأدمن (CRUD + صورة + تقييم + تفعيل/تعطيل) - Admin\ShopController
  • FR-29..30: إدارة المخزون وطلبات التزويد - Admin\SparePartController
  • FR-31: إدارة الملحقات - Admin\AccessoryController
  • إدارة الفنيين وعمال التوصيل (بدون كلمة مرور - OTP فقط للدخول من الجوال، أو Email/Password من لوحة الفني)
  • تدفق التوصيل الكامل: قبول → في الطريق → وصل → تأكيد + تحصيل كاش
  • نظام إشعارات مزدوج: Push (FCM) + إشعارات داخل التطبيق (قاعدة بيانات) لكل الأدوار الأربعة
  • حظر المتاجر (is_active=false) يمنع الطلبات الجديدة عليها فوراً من كل الواجهات

2.2 المتطلبات غير الوظيفية (Non-Functional Requirements)

2.2.1 الأداء (Performance)

  • كل قوائم البيانات (Maintenance Requests, Orders, Deliveries, Shops, Technicians...) تستخدم Pagination (15 عنصر/صفحة) بدل جلب كل الجدول - يمنع استهلاك ذاكرة عالٍ مع نمو البيانات.
  • استخدام Eager Loading (with('customer', 'shop', 'parts')) في كل مكان لتفادي مشكلة N+1 queries.
  • حساب المسافة الجغرافية (Haversine) يتم داخل استعلام SQL واحد (selectRaw) بدل جلب كل الصالات وحسابها في PHP - أسرع وأقل استهلاك ذاكرة.
  • FCM Access Token يُخزَّن في Cache لمدة 55 دقيقة بدل طلب token جديد من Google في كل إشعار - يوفر round-trip كامل لكل إشعار.
  • نقطة ضعف حالية: لا يوجد Queue فعلي لإرسال الإشعارات (FCM يُرسَل بشكل متزامن Synchronous ضمن نفس الـ request) - لو تأخرت استجابة Google/Firebase سيتأخر رد الـ API معها. الحل المستقبلي: تفعيل QUEUE_CONNECTION=database فعلياً مع Jobs بدل الاستدعاء المباشر.

2.2.2 الأمان (Security)

تفصيل كامل في القسم 14. ملخص سريع: Sanctum tokens منفصلة لكل دور، تشفير كلمات المرور bcrypt، Rate Limiting على OTP، لا secrets في الكود (كلها في .env)، Form Requests تتحقق من كل مدخل قبل وصوله لقاعدة البيانات.

2.2.3 قابلية التوسع (Scalability)

  • المعمارية Stateless بالكامل (REST + Token-based auth) - يمكن تشغيل عدة نسخ من السيرفر خلف Load Balancer بدون مشاكل جلسات (لا يوجد اعتماد على PHP Session للـ API نفسه).
  • فصل واضح بين الأدوار الأربعة (Guards منفصلة) يسمح مستقبلاً بفصل كل دور في microservice مستقل لو لزم الأمر بدون إعادة هيكلة جذرية.
  • نقطة اختناق محتملة: قاعدة بيانات MySQL واحدة بدون Read Replicas - مقبول لحجم المشروع الحالي (مشروع تخرج/شركة ناشئة) لكن يحتاج مراجعة لو زاد عدد الصالات لعشرات الآلاف من الطلبات يومياً.

2.2.4 الموثوقية والتوفر (Reliability & Availability)

  • كل عملية تُغيّر عدة جداول مرتبطة (checkout، الموافقة على التشخيص) مغلّفة بـ DB::transaction() - إما تنجح كل الخطوات أو تتراجع كلها، فلا توجد بيانات نصف-محدَّثة.
  • إرسال FCM محاط بـ try/catch في كل مكان - فشل الإشعار لا يوقف نجاح العملية الأساسية أبداً (مبدأ "fire-and-forget").
  • قيد خارجي مكتشف فعلياً في هذا المشروع: استضافة مشتركة سورية + حظر جغرافي من Google لخدمة Gemini AI (راجع القسم 15) - مثال حي على أن التوفر لا يعتمد فقط على الكود بل على القيود الجغرافية/السياسية للخدمات الخارجية المستخدمة.

2.2.5 قابلية الصيانة (Maintainability)

  • كل Endpoint له Form Request مستقل لقواعد التحقق - الكونترولر لا يحتوي منطق تحقق مباشر (Separation of Concerns).
  • تسمية موحدة للاستجابات: { "message": "...", "data": {...} } في كل مكان - يسهّل على فريق الموبايل بناء طبقة استدعاء API عامة (Generic API client).
  • الحالات النشطة لطلب الصيانة موحّدة في ثابت واحد MaintenanceRequest::ACTIVE_STATUSES ويُستخدم في أكثر من كونترولر (حالة توفر الصالة، حالة انشغال الفني) بدل تكرار المصفوفة في كل مكان.

2.2.6 قابلية الاستخدام (Usability)

  • رسائل الأخطاء بصيغة JSON منظمة وواضحة (422 يرجع errors لكل حقل بشكل منفصل) - تسهّل على الموبايل عرض رسالة مناسبة لكل حقل.
  • حالتان منفصلتان لطلب الصيانة (status للفني/النظام، customer_status للعميل) - تفصل بين "أين الطلب تقنياً" و"ماذا يجب أن يرى العميل" لتفادي حالات فنية معقدة تظهر للمستخدم النهائي.

4. نظام المصادقة

4.1 دخول العملاء - OTP بثلاث خطوات

الخطوة 1 - طلب OTP:

POST /api/v1/customer/send-otp Body: { "phone": "+963912345678" } Response 200: { "message": "OTP sent successfully" } Response 429: { "message": "Too many attempts..." } ← أكثر من 3 في 60 ثانية

الخطوة 2 - التحقق:

POST /api/v1/customer/verify-otp Body: { "phone": "+963912345678", "code": "12345" } مستخدم جديد → 200: { "data": { "is_new_user": true, "phone": "..." } } مستخدم موجود → 200: { "data": { "customer": {...}, "token": "1|abc..." } } كود خاطئ → 422: { "message": "Invalid or expired OTP." }

الخطوة 3 - تسجيل (للجدد فقط):

POST /api/v1/customer/register Body: { "first_name":"أحمد", "last_name":"محمد", "phone":"+963912345678", "email":"a@a.com", "birthdate":"1995-01-15" } Response 201: { "data": { "customer": {...}, "token": "2|xyz..." } } ⚠ يتحقق من وجود OTP بـ phone_verified=true خلال 10 دقائق

4.2 دخول الفنيين - Email + Password (مثل الأدمن)

الفني يدخل من نفس لوحة التحكم باستخدام Email + Password. يُنشأ حسابه من الأدمن ولا علاقة له بـ OTP.
POST /api/v1/auth/login Body: { "email": "tech@shamsung.com", "password": "password123" } نجاح (فني) → 200: { "data": { "role": "technician", "user": {..., "shop":{...}}, "token":"..." } } نجاح (أدمن) → 200: { "data": { "role": "admin", "user": {...}, "token":"..." } } بيانات خاطئة → 401: { "message": "Invalid credentials." } حساب موقوف → 403: { "message": "Your account has been deactivated." } ⚠ يبحث في جدول admins أولاً، فإن لم يجد يبحث في technicians

UnifiedAuthController: هو المتحكم المسؤول - يخدم الأدمن والفني معاً من نفس الـ endpoint.

4.3 دخول عمال التوصيل - OTP بخطوتين

POST /api/v1/delivery/send-otp POST /api/v1/delivery/verify-otp ← نفس منطق الفني تماماً

4.4 دخول الأدمن - Email/Password

POST /api/v1/auth/login Body: { "email": "admin@shamsung.com", "password": "password123" } Response: { "data": { "role": "admin", "user": {...}, "token": "..." } } ← نفس الـ endpoint للفني الذي لديه email/password: Response: { "data": { "role": "technician", "user": {..., "shop":{...}}, "token":"..." } } يبحث في admins أولاً، ثم technicians إذا لم يجد: 401 Invalid credentials

4.5 استخدام الـ Token في كل request محمي

Authorization: Bearer {token} Accept: application/json
الـ Tokens لا تنتهي تلقائياً (expiration=null). تُحذف فقط عند logout أو عند استدعاء tokens()->delete().

4.6 أهم أسطر الكود في منطق المصادقة

UnifiedAuthController::login() - المسؤول عن Admin + Technician معاً

$admin = Admin::where('email', $email)->first(); if ($admin && Hash::check($password, $admin->password)) { $token = $admin->createToken('admin_token')->plainTextToken; return response()->json(['data' => ['role' => 'admin', 'user' => $admin, 'token' => $token]]); } $technician = Technician::where('email', $email)->first(); if ($technician && Hash::check($password, $technician->password)) { if (! $technician->is_active) { return response()->json(['message' => 'Your account has been deactivated.'], 403); } $token = $technician->createToken('technician_token')->plainTextToken; return response()->json(['data' => ['role' => 'technician', 'user' => $technician->load('shop'), 'token' => $token]]); } return response()->json(['message' => 'Invalid credentials.'], 401);

لماذا مهم: نفس الـ endpoint (/auth/login) يخدم دورين مختلفين - القرار يُتَّخذ بناءً على أي جدول يحتوي الإيميل، وليس بناءً على حقل "role" يرسله المستخدم (لتفادي انتحال الشخصية بإرسال role خاطئ).

OtpService::sendOtp() - Rate Limiting الفعلي

$key = 'otp-send:' . $phone; if (RateLimiter::tooManyAttempts($key, maxAttempts: 3)) { return false; // Controller يرجعها 429 } RateLimiter::hit($key, decaySeconds: 60); $code = (string) random_int(10000, 99999); Otp::create(['phone' => $phone, 'code' => $code, 'expires_at' => now()->addMinutes(10)]);

لماذا مهم: الـ Rate Limiter مبني على مفتاح لكل رقم هاتف (ليس IP)، فمنع الإساءة يبقى فعّالاً حتى لو المهاجم غيّر الشبكة/IP باستمرار. الـ key بالكامل يعتمد على cache driver الافتراضي (database هنا حسب .env: CACHE_STORE=database).

OtpService::verifyOtp() - التمييز بين مستخدم جديد وموجود

$otp = Otp::where('phone', $phone)->where('code', $code) ->where('is_used', false)->where('expires_at', '>', now())->latest()->first(); if (! $otp) return 'otp_invalid_or_expired'; $otp->update(['is_used' => true]); $user = $this->findByPhone($phone, $guard); if (! $user) { $otp->update(['phone_verified' => true]); // يسمح بـ register خلال 10 دقائق return 'user_not_found'; } if (isset($user->is_active) && ! $user->is_active) { return 'account_deactivated'; } return ['token' => $user->createToken("{$guard}_token")->plainTextToken, 'user' => $user];

ملاحظة أمان: الـ OTP يُعلَّم is_used=true فوراً بعد أول تحقق ناجح - لا يمكن إعادة استخدامه، حتى لو حاول أحد إعادة إرسال نفس الطلب (replay attack).

6.2 FcmService

الملف: app/Services/FcmService.php

بيانات الاعتماد: storage/app/firebase-credentials.json (service account)

مشروع Firebase: shamsoung-d2d58

لا يوجد package خارجي. الكود يبني JWT بـ RS256 يدوياً باستخدام PHP OpenSSL ويستدعي FCM HTTP v1 API مباشرة.

send(string token, string title, string body, array data): void

إرسال إشعار Push لجهاز واحد. جميع FCM calls هي fire-and-forget (تُسجَّل الأخطاء ولا تُوقف الـ request).

إرسال إشعار لعدة أجهزة. يُرسل لكل token على حدة في loop.

آلية العمل الداخلية

  1. getAccessToken(): يتحقق من كاش 'fcm_access_token' - إذا موجود يرجعه مباشرة
  2. fetchAccessToken(): يبني JWT ويرسله لـ Google OAuth2 endpoint للحصول على access token جديد
  3. buildJwt(): يبني JWT بـ header(RS256) + payload(iss,scope,aud,iat,exp) + signature بالمفتاح الخاص
  4. يخزن الـ token في كاش لمدة 55 دقيقة (FCM tokens تنتهي بعد 60 دقيقة)

بنية الـ data payload في كل إشعار

// صيانة: { "type": "maintenance_request", "id": "123" } // استشارة: { "type": "consultation", "id": "45" } // حساب: { "type": "account_status", "is_active": "1" } // توصيل: { "type": "delivery", "id": "67" }

6.3 ShopService

الملف: app/Services/ShopService.php

findNearestShops(float lat, float lon, int radiusKm = 50): Collection

يستخدم معادلة Haversine في SQL لحساب المسافة بين نقطتين على الكرة الأرضية.

SELECT shops.*, ( 6371 * acos( cos(radians(?)) * cos(radians(latitude)) * cos(radians(longitude) - radians(?)) + sin(radians(?)) * sin(radians(latitude)) ) ) AS distance FROM shops WHERE is_active = 1 HAVING distance <= 50 ORDER BY distance ASC

تُرجع Collection من الصالات النشطة مرتبة من الأقرب للأبعد، مع حقل distance بالكيلومتر.

14. الأمان والحماية (Security)

14.1 المصادقة والتفويض

  • Laravel Sanctum لكل الأدوار الأربعة - كل دور له Guard/Model منفصل تماماً (لا يوجد جدول users مشترك)، فمهما حصل لا يستطيع Token خاص بعميل الوصول لـ endpoint خاص بأدمن ولو حاول تغيير الـ Authorization header يدوياً - الـ middleware auth:sanctum يتحقق من نوع الـ Model المرتبط بالتوكن.
  • كلمات المرور (Admin/Technician/DeliveryWorker) مخزَّنة بـ bcrypt عبر Eloquent cast 'password' => 'hashed' - لا يوجد md5/sha1 بأي مكان.
  • Customer/Technician/DeliveryWorker: password nullable لأنها لا تُستخدَم أصلاً (الدخول بـ OTP) - Technician فقط له كلمة مرور اختيارية إضافية للدخول من لوحة التحكم.
  • authorize() في كل Form Request يرجع true دائماً - هذا مقصود: التفويض (من يقدر يرى ماذا) يتم عبر منطق الكونترولر نفسه (مثال: MaintenanceRequest::where('customer_id', $customer->id)) وليس عبر Form Request. الفصل بين "هل البيانات صحيحة الشكل" (Form Request) و"هل يحق لهذا المستخدم الوصول لهذا السجل" (Controller) مقصود ومتعمَّد.

14.2 حماية من الإساءة (Abuse Prevention)

  • Rate Limiting على OTP: 3 محاولات إرسال لكل رقم هاتف كل 60 ثانية (RateLimiter مفتاحه رقم الهاتف، لا الـ IP) - يمنع OTP-bombing حتى لو المهاجم بدَّل شبكته.
  • الـ OTP يُعلَّم is_used=true فور أول استخدام ناجح - لا Replay Attack.
  • الـ OTP له صلاحية 10 دقائق فقط (expires_at) - نافذة زمنية ضيقة.
  • حسابات الفني/عامل التوصيل الموقوفة (is_active=false) تُرفَض فوراً عند verifyOtp() قبل حتى إصدار أي Token - 403.

14.3 حماية البيانات والمدخلات

  • Mass Assignment Protection: كل Model يحدد $fillable صراحة - لا يوجد $guarded = [] بأي مكان، فلا يقدر أحد يمرر حقل زي is_active أو id ضمن بيانات غير متوقعة ويُقبل بالخطأ.
  • SQL Injection: كل الاستعلامات عبر Eloquent/Query Builder مع Parameter Binding - الاستثناء الوحيد لـ Raw SQL هو معادلة Haversine بـ ShopService، وهي تستخدم selectRaw(..., [$lat, $lon, $lat]) بـ placeholders (?) وليس string concatenation - آمنة.
  • رفع الملفات: كل Form Request لصور (Shop/Accessory/Consultation/Delivery confirmation) يتحقق image, max:5120KB - يرفض أي امتداد غير صورة قبل الوصول لـ Storage.
  • لا Secrets بالكود: كل المفاتيح الحساسة (GEMINI_API_KEYS، Firebase credentials، DB password) في .env أو storage/app/firebase-credentials.json - خارج git بالكامل (.gitignore).

14.4 قيود معروفة بالأمان (تحتاج تحسين مستقبلاً)

  • Sanctum Tokens لا تنتهي صلاحيتها أبداً (expiration=null بالإعدادات الافتراضية) - لو سُرِّب توكن يبقى صالحاً للأبد حتى يُحذَف يدوياً. التحسين المقترح: تفعيل 'expiration' => 60*24*30 (شهر مثلاً) بـ config/sanctum.php.
  • لا يوجد 2FA لحسابات الأدمن (فقط Email+Password).
  • لا Audit Log لتتبع من غيَّر ماذا وقتها (فقط created_at/updated_at على مستوى السجل، بدون سجل تاريخي كامل للتغييرات).

15. القيود المعروفة والتحديات التقنية

15.1 حظر Google Gemini API جغرافياً عن سوريا

المشكلة الفعلية المُكتشَفة: السيرفر مستضاف على استضافة سورية (shamsung.haderin.sy). عند استدعاء Gemini API مباشرة، Google يرفض الطلب بـ:

HTTP 400 - FAILED_PRECONDITION "message": "User location is not supported for the API use."

هذا قيد جغرافي إلزامي من Google (متعلق بعقوبات/قيود تصدير أمريكية) - لا حل له على مستوى الكود أو إعدادات السيرفر. تأكَّدنا أن المفاتيح نفسها صحيحة وغير منتهية (تعمل 200 OK لما تُستدعى من مكان آخر خارج سوريا).

الحل المُطبَّق: بروكسي عبر Cloudflare Workers (مجاني) - السيرفر السوري يرسل الطلب لعنوان الـ Worker (خارج سوريا جغرافياً بحكم شبكة Cloudflare العالمية)، والـ Worker يمرره لـ Google ويرجع الرد. تفعيله عبر متغيرين اختياريين بـ .env:

GEMINI_PROXY_URL=https://gemini-proxy.xxx.workers.dev GEMINI_PROXY_SECRET=<نص سري يتحقق منه الـ Worker> // داخل ConsultationController::callGeminiApi() $url = $proxyUrl ? rtrim($proxyUrl,'/') . $path : "https://generativelanguage.googleapis.com{$path}";

لو المتغيرين فارغين بـ .env، الكود يرجع تلقائياً للاتصال المباشر (Backward Compatible) - مفيد للتطوير المحلي خارج سوريا.

15.2 تحديات أخرى

  • استضافة مشتركة بدون Terminal/SSH: كل الأوامر (migrate، composer install، حتى فحص ملفات اللوغ) تحتاج تُنفَّذ يدوياً عبر لوحة الاستضافة (cPanel File Manager) أو تُشغَّل من بيئة محلية ثم تُرفَع الملفات يدوياً - لا CI/CD تلقائي حالياً.
  • لا Queue فعلي: QUEUE_CONNECTION=database لكن الإشعارات (FCM) تُرسَل Synchronous ضمن نفس الـ request - في حال بطء Firebase/Google يتأخر رد الـ API معه (محمي بـ try/catch فلا يفشل، لكن قد يبطّئ).
  • لا اختبارات آلية (Automated Tests) مكتوبة فعلياً حالياً رغم وجود phpunit.xml وأمر composer test جاهز - القاعدة موجودة لكن Test Cases الفعلية للـ business logic (مثال: approve()، checkout()) لم تُكتب بعد.
  • لا نموذج ربط فني↔طلب صيانة مباشر: أي فني بنفس الصالة يقدر يتعامل مع أي طلب لتلك الصالة (لا يوجد technician_id على maintenance_requests) - قرار تصميم مقصود لتوزيع العمل، لكنه يعني أن "مشغول/متاح" للفني الفردي هو تقدير على مستوى الصالة وليس دقيقاً 100% على مستوى الفرد.

هذه الأسئلة مبنية على القرارات التصميمية الفعلية بالمشروع - الإجابة الجيدة تشرح لماذا اتُّخذ القرار، مو بس تعيد وصف الكود.

17.1 أسئلة معمارية عامة

س: ليش REST API منفصل تماماً عن الواجهة بدل Laravel Blade التقليدي؟

ج: المشروع يخدم 3 عملاء مختلفين تماماً بنفس الوقت: تطبيقات موبايل (iOS/Android) ولوحة تحكم React منفصلة. REST API + JSON هو القاسم المشترك الوحيد بينهم - أي واجهة عرض (Blade) كانت رح تخدم واحد منهم بس وتحتاج تُبنى إضافياً. الفصل الكامل بين الـ Backend (API) والـ Frontend يسمح لكل فريق يشتغل ويُطوَّر بشكل مستقل تماماً.

س: ليش 4 أدوار بـ Guards منفصلة بدل جدول users واحد مع عمود role؟

ج: كل دور له حقول وسلوك مختلف جذرياً (العميل بلا كلمة مرور أصلاً، الفني له shop_id إلزامي، الأدمن بلا OTP إطلاقاً). جدول واحد بعمود role كان سيحتاج عشرات الأعمدة nullable حسب الدور (denormalization سيئة) وتحقق شرطي معقد بكل مكان ("لو role=customer تحقق كذا..."). الفصل لجداول/Models منفصلة أوضح، وأهم من هيك: يمنع تماماً احتمال تسرّب صلاحيات بين الأدوار (توكن عميل لا يمكن نظرياً أن يُقرأ كتوكن أدمن، لأنهم من نموذج مختلف بالكامل من ناحية Sanctum).

س: ليش Sanctum وليس Passport أو JWT يدوي؟

ج: Passport مصمَّم لـ OAuth2 الكامل (مفيد لما يكون في third-party apps تتصل بواجهتك) - overkill هون لأن العميل والـ Frontend كلاهما "أول طرف" (first-party). Sanctum أخف وأبسط، ويدعم بالضبط الحاجة: token واحد بسيط لكل جهاز/جلسة، مربوط مباشرة بالـ Model عبر HasApiTokens trait، بدون تعقيد إضافي.

17.2 أسئلة عن قرارات تصميم محددة

س: ليش فيه status وcustomer_status منفصلين بطلب الصيانة؟

ج: status يمثّل الحالة "الفنية/الداخلية" الحقيقية (pending, under_inspection...) التي يفهمها الفني والنظام. customer_status يمثّل "ماذا يجب أن يرى العميل تحديداً" (pending_approval, approved, rejected) - وهي أبسط وأقل تفصيلاً. هذا يفصل منطق سير العمل الداخلي عن تجربة عرضه للمستخدم النهائي، ويسمح مستقبلاً بتغيير إحداهما بدون كسر الأخرى.

س: ليش القطع (parts) تُنسَخ (name, price) من SparePart بدل الاكتفاء بـ Foreign Key؟

ج: هذا نمط "Snapshot/Denormalization" مقصود. سعر القطعة بكتالوج SparePart قابل للتغيير لاحقاً (الأدمن يقدر يعدّل الأسعار). لو الطلب اكتفى بـ spare_part_id فقط، وتغيَّر السعر لاحقاً، سيظهر سعر مختلف بفاتورة/تشخيص قديم عن السعر وقت إنشائه فعلياً - وهذا خطأ محاسبي. النسخ وقت التشخيص (diagnose()) يجمّد السعر والاسم كما كانا في تلك اللحظة بالضبط، بغض النظر عن أي تغيير لاحق بالكتالوج.

س: ليش checkout() ينشئ طلبية منفصلة لكل صالة بدل طلبية واحدة؟

ج: كل صالة (Shop) هي كيان تشغيلي مستقل (له مخزونه، فريق توصيله الخاص). لو العميل اشترى من صالتين بنفس السلة، كل صالة يجب تشحن/تجهّز طلبها بشكل مستقل تماماً - فصل الطلبية يعكس هذا الواقع التشغيلي، ويسمح لكل صالة تتبع طلبيتها وتحصيلها المالي بمعزل عن الأخرى.

س: ليش الموقع الجغرافي (lat/long) بيُنسَخ على جدول deliveries وليس على maintenance_requests أو orders نفسها؟

ج: الموقع مطلوب فقط باللحظة يلي حدا رح يتحرك فيزيائياً لعند العميل (delivery)، مش وقت تقديم الطلب نفسه (اللي ممكن ياخد أيام لحتى يوصل لمرحلة التوصيل). ربطه بجدول deliveries يخليه يتسجل بأحدث لحظة ممكنة (approve()/checkout()) بدل تخزينه بدري وقد يصير قديم/غير دقيق وقت التوصيل الفعلي، وبنفس الوقت ما بيكرر الحقل بجداول ثانية ما إلها علاقة مباشرة بالتوصيل.

س: ليش نقل estimated_time من الأدمن إلى عامل التوصيل نفسه؟

ج: الأدمن وقت إنشاء التوصيلة ما بعرف مين رح ياخدها ولا وين هو جغرافياً - أي رقم يحطه تخمين عشوائي. عامل التوصيل هو الوحيد يلي بيعرف فعلياً موقعه الحالي وظروف الطريق لحظة قبوله الطلب، فتقديره أدق بكثير. هذا مثال على مبدأ "أقرب شخص للمعلومة هو يلي لازم يوفرها" (Single Source of Truth بأقرب نقطة ممكنة للواقع).

17.3 أسئلة عن الأداء وقابلية التوسع

س: كيف بتضمن ما يصير Race Condition بخصم المخزون (stock_quantity) لو طلبين إجو بنفس اللحظة؟

ج: العملية محاطة بـ DB::transaction()، واستخدام decrement() بـ Eloquent يترجم لـ SQL يشبه UPDATE ... SET stock_quantity = stock_quantity - X - وهو atomic على مستوى قاعدة البيانات نفسها (MySQL يقفل الصف أثناء التحديث). نقطة تحسين ممكنة مستقبلاً: إضافة تحقق صريح WHERE stock_quantity >= X ضمن نفس الاستعلام (بدل تحقق منفصل قبل الـ decrement) لمنع negative stock بشكل مضمون 100% تحت ضغط عالٍ جداً من الطلبات المتزامنة.

س: ليش معادلة المسافة (Haversine) بـ Raw SQL بدل مكتبة GIS؟

ج: MySQL Spatial Extensions (ST_Distance_Sphere مثلاً) تحتاج أعمدة من نوع خاص (POINT) وإعداد إضافي غير موجود بالبنية الحالية. لعدد صالات محدود (عشرات وليس ملايين)، معادلة Haversine بـ selectRaw كافية جداً من ناحية الأداء وأبسط بالتطبيق - لا حاجة لتعقيد إضافي غير مبرَّر بحجم البيانات الحالي (YAGNI - You Aren't Gonna Need It).

س: شو أكبر نقطة ضعف بالأداء حالياً؟

ج: إرسال FCM بشكل متزامن (Synchronous) ضمن نفس الـ request بدل استخدام Queue فعلي - لو تأخرت Google/Firebase حتى بضع ثوانٍ، يتأخر رد الـ API كامل معها رغم إنو العملية الأساسية (مثلاً إنشاء الطلب) خلصت فعلياً. الحل: تفعيل Job/Queue حقيقي لإرسال الإشعارات بشكل غير متزامن تماماً.

17.4 أسئلة عامة متوقعة بأي مناقشة تخرج

س: شو الفرق بين المتطلبات الوظيفية وغير الوظيفية بمشروعك؟ عطيني مثال من الكود نفسه.

ج: وظيفي = "شو بيعمل النظام" (مثال: العميل يقدر يقدّم طلب صيانة - MaintenanceRequestController::store). غير وظيفي = "كيف بيعمله بجودة/بشكل صحيح" (مثال: نفس العملية محمية بـ DB::transaction عشان الموثوقية، ومحدودة الحقول المسموحة عبر Form Request عشان الأمان، ومُرقَّمة صفحات (pagination) عشان الأداء). تفصيل كامل بالقسم 2.
